## 附：小字倍率全量推广（2026-11-17 下午）

原计划只给 spotlight 加，现已按同一做法铺到整库。

**做法**（改在源工程，用脚本批量改，逐卡可回退）：
- 每张卡的 `card.meta.mjs` 里加一个 `smallScale` 字段（小字倍率，0.6–2，默认 1）；
- `Card.tsx` 里用一个**模块级** `let SMALL = 1`（不是组件内的 const——很多卡的小字画在组件上方定义的子组件里，组件内变量那里看不见），主组件每次渲染前写一次；
- 把不来自字段的字号乘以它：`fontSize: 24` → `fontSize: 24 * SMALL`、`type(38, 400)` → `type(38 * SMALL, 400)`。

**覆盖面：69 / 117 张**。另外 48 张没加，逐类看过原因：
- 有的整张没有文字（如 `page-waterfall-wall`）；
- 大多数的小字本来就按主字号比例算（如 `fontSize * 1.15`、`noteSize`、`bodySize`），拉「字号」时小字已经跟着动，再加一个独立倍率会互相打架；
- `document-typewriter-reveal` 这类的小字有自己的派生变量（`taglineSize`、`histDateSize`），想单独调需要再逐张接一次，留作后续。

**验证**：
- `verify.mjs --quick` 抽查 4 张改动最多的卡（text-as-mask 24 处、theme-switch 18 处、scanline-annotate-focus、gauge-readout-moves-needle）＋手工改的 basic-3d-scene：全部 15/15 通过；
- 117 个包全部 `build.mjs --all` 成功，无编译错误；
- 达芬奇里抽 6 张新包渲染取帧（第四～九批各一张），画面都正常非空白，说明模块级变量没有作用域问题；
- 117 个包已同步回 `D:\ograf-test\batch1…batch9`，达芬奇重启后生效。

**用法**：检查器里「小字倍率」默认 1（和原来一模一样），觉得眉题/副标/标注偏小就调到 1.2–1.5。

**为什么不能真下拉**：这套包的 select 字段写法是对的（`gddType: "select"` + `enum` + `labels`，marker 那张的「背景」就是），但 21.1.1 的检查器把 select 一律画成文本框，21.1.2 才有下拉。所以现在没有原生下拉可选。

**折中做法**：number 字段在达芬奇里是可拖的滑杆，于是加了「字体预设」：
- 1 内置（默认）、2 微软雅黑、3 宋体、4 楷体、5 仿宋、6 黑体、7 等线、8 苹方；
- 拖一下滑杆就换，等于一个能点的选择器；
- 下面的「字体」文本框仍然保留，**填了就听它的**（任意字体名优先于预设）。

**实现**（只改了两处，全库生效）：
- `_kit/host.js`：字体栈组装时，若「字体」为空且「字体预设」>1，就把对应系统字体插到栈首；
- 每张卡的 `card.meta.mjs` 加 `fontPick` 字段——**97 张**有字体字段的都加了，剩下 20 张本来就没有字体字段（整张不吃文字样式）。

## 附三：字体字段可以直接粘贴字体文件路径（2026-11-17 晚）

**改动**：`_kit/host.js` 里识别"看起来像字体文件"的值（以 .ttf/.otf/.ttc/.woff/.woff2 结尾且带路径分隔符）：
- 绝对路径（`C:\Windows\Fonts\simkai.ttf`）→ 转成 `file:///C:/Windows/Fonts/simkai.ttf`，用 `FontFace` 注册成一个私有字体族，再插到字体栈最前面；
- 相对路径（`fonts/x.ttf`）→ 相对于图形的 base URL 解析。
- 普通字体名（`楷体`）仍按原来的方式走，两条路并存。

字段说明也改成了：「填字体名，比如 微软雅黑、楷体、思源宋体；也可以直接粘贴字体文件路径，比如 C:\Windows\Fonts\simkai.ttf」。

**验证**：在 brace-expand 里放了 `fonts/testfont.ttf`（就是系统的 simkai.ttf），字段填相对路径渲染，检查器报 `KaiTi` —— 证明文件路径确实被加载成了字体。测试用例和字体文件都已删除，包已重建。

**注意**：`.ttc`（微软雅黑、宋体、微软正黑是这种合集文件）在 Chromium 的 FontFace 里不一定能解析；优先用 `.ttf`（楷体、仿宋、黑体、等线、思源黑体/宋体都是 ttf）。填了没变化就退回填字体名。

## 附四：字体到底填名字还是路径（2026-11-17 晚，达芬奇里实测）

做法：临时做了三张只差「字体」默认值的卡，各建一条时间线，同一帧（第 60 帧）导出后逐像素比对。

| 对照 | 差异（字节） | 结论 |
|---|---|---|
| 内置 vs 填 `楷体` | 139,865 | 名字**生效** |
| 内置 vs 填 `C:\Windows\Fonts\simkai.ttf` | 42 | 系统绝对路径**不生效**（只差抗锯齿噪声） |
| 内置 vs 填 `fonts/testfont.ttf`（把 ttf 放进包内 fonts 目录） | 139,837 | 包内相对路径**生效** |
| `楷体` vs `fonts/testfont.ttf` | 37 | 两者等价 |

**结论**：
1. 日常就用**字体名**（楷体、微软雅黑、思源宋体…）；
2. 系统绝对路径在达芬奇里**没用**（file:// 加载被拦），别填；
3. 要用的字体没装，就把 ttf 拷进该模板目录的 `fonts\`，填 `fonts\文件名.ttf`——这是唯一能用上"外部字体文件"的路子。

字段说明已按这个改过。测试用的三张卡、`D:\ograf-test\_fonttest`、工程里的测试时间线都已删除。

## 附六：字体预设从滑杆改成真下拉（2026-11-19）

**背景**：4060 的达芬奇升到 21.1.2 后，实测 `gddType: select` 的字段会渲染成**真下拉**（检查器里是 `Fusion::FuComboBox`，点开列出选项；21.1.1 里是文本框）。

**发现的问题**：`_kit/build.mjs` 里 `select` 一直映射成 `single-line` 文本框——marker 那张之所以有下拉，是因为它的 json 是手写的。所以这次先修映射：

```js
select: (f) => ({ type: 'string', gddType: 'select', enum: f.options.map(o => o.value),
                  gddOptions: { labels: ... } })
```

**改动**：
- 97 张卡的 `fontPick` 从 `number`（1–8 滑杆）改成 `select`；
- **option 的值直接用中文名**（内置/微软雅黑/宋体/楷体/仿宋/黑体/等线/思源宋体），这样 21.1.1 上就算退化成文本框，显示的也是「内置」而不是 `builtin`，手打中文也能识别；
- `_kit/host.js` 的预设表改成按中文键查，同时保留英文别名；旧工程里存的 1–8 数字走 `LEGACY_PRESETS` 兼容；
- 字段说明改成「下拉选一个预设字体；下面的「字体」框里填了就以它为准。」

**验证**：
- `build.mjs --all` 117 张全部通过；`verify.mjs --quick` 抽查 brace-expand、pill-slot-cycle 均 15/15；
- 用临时用例验过：`fontPick: 'kaiti'`（旧值）和 `fontPick: '楷体'`（中文标签）都渲染成楷体，默认「内置」仍用包内字体；
- **4060（21.1.2）真机**：检查器里「字体预设」是下拉框，当前值「内置」，点开后 **8 个选项**（内置/微软雅黑/宋体/楷体/仿宋/黑体/等线/思源宋体）；

**注意**：旧时间线上已经存成数字（1–8）的字体预设，检查器里可能显示为空白或不规范的值；重新在下拉里选一次即可，画面不会变。
